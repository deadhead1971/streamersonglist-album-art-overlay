# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A tool for music streamers using StreamerSonglist. One app — the **dashboard** (`python -m app.dashboard`, or `run_dashboard.bat`) — a local Flask app at `http://127.0.0.1:5050`. It syncs the songlist from the StreamerSonglist API, bulk-proposes artwork via iTunes Search, and provides a review UI to confirm/reject/upload images. On startup it also launches the **runtime service** (`app/runtime.py`): a background thread that resolves the current song (live SSL queue top, or a text file in `file` song-source mode), writes `current_artwork.png` for OBS, and feeds the **queue overlay** (`/overlay/queue`, an OBS browser source; configured at `/overlay`). The dashboard is the only process, offline and during a live stream. (A standalone headless watcher existed historically; it was folded into the runtime service in July 2026.)

`README.md` is user-facing. (`PLAN.md`, the original build plan with design decisions — API facts, rate limits, validation rules — is kept locally and not committed; ignore references to it if you don't have the file.)

## Commands

- Install: `pip install -r requirements.txt` (Flask, requests, Pillow, centrifuge-python). `centrifuge-python` pulls `protobuf` unpinned — in a shared environment install `protobuf<6` afterwards or it breaks tensorflow / google-api-*.
- Run dashboard: `python -m app.dashboard`
- Diagnostics/maintenance (all under `tools/`): `python -m tools.probe_api` (read-only check of the API, token, channel and queue — never prints the token); `python -m tools.upgrade_art [--apply]` (re-fetches stored iTunes covers at `sources.ITUNES_ART_SIZE`; dry run by default, refuses while the dashboard runs, keeps originals in `library/pre-upgrade/`, carries the art wall's hidden-cover keys over).
- No tests or linter are configured. Verify by running the app; logs go to `artwork_fetcher.log` (rotated, 2MB x 4). If you go looking for an overlay poll and can't find it, that is deliberate: `artwork._DropPollingRequests` drops the *successful* werkzeug access lines for the four polled endpoints (`/overlay/queue.json`, `/overlay/current.json`, `/api/runtime/status`, `/img?`), which were 79% of the log measured on 2026-08-31 - about 2,200 lines an hour saying nothing happened. 4xx/5xx on those paths, page loads, POSTs and every app-logged line are kept.

Windows environment (PowerShell 5.1); paths contain spaces — quote everything in `.bat` files.

## Architecture

Modules in `app/`:

- `config.py` — owns every path, split in two: `RESOURCE_DIR` (read-only files shipped with the app: `config.example.json`, `obs/`) and `DATA_DIR` (everything the app writes: `config.json`, `library/`, the log, and an installed copy's `obs/` loaders). From source both are the repo root, as they always were. Frozen (`FROZEN`, a PyInstaller build) data goes to `%LOCALAPPDATA%\AlbumArtOverlay`, because an upgrade replaces the program folder. The env var `ALBUMART_DATA_DIR` overrides it in either mode, for CI or to point `tools/` at an installed copy. When the two differ (`SEPARATE_DATA_DIR`), `dashboard.sync_obs_loaders` copies the loaders out on every start (only if the bytes changed), and a first run pre-fills `output_image` in the data folder. Never build a path from `__file__` elsewhere. It loads and saves `config.json` (gitignored; created from `config.example.json` on first run). All tunables live here: username, song source, output/fallback image paths, `skip_artists`, reflection settings. Saved atomically via `fileio`, read as `utf-8-sig` (a BOM from a Windows editor used to read as all-default settings).
- `fileio.py` — `write_atomic` (temp file + fsync + `os.replace`, retried ~1s through Windows sharing violations, then **raises** — never falls back to writing in place) and a matching `read_bytes`. Used for everything that can't be regenerated: the manifest and its `.bak`, library images, `config.json`. The OBS output PNG deliberately keeps `imaging.atomic_save_image`'s own rules instead.
- `songlist.py` — StreamerSonglist API client for the **v2 API only**. v2 went live on 2026-08-12; v1 is retired (its URLs answer with v2's own 404, checked 2026-09-25) and its code was removed. The client used to pick v1/v2 by probing once per session with "404 means v1" — which v2's 404 for an *unknown username* turned into a trap: one Test-connection typo cached "v1" process-wide, so the corrected name, and the running live service, failed until a settings save. There is no detection now, and 404 `streamer not found` becomes `StreamerNotFound` with a plain-English message (a settings mistake: the runtime banners it like `AuthRequired`, and the settings save reports it as the username, not the token). Every read needs the configured token and the queue splits into a `playing` slot plus upcoming-only `items`. v2 accepts **three** Authorization prefixes and `api_token_type` picks which is sent: `User` (profile → API Access, every channel the account admins), `Streamer` (a channel's Settings → Access, that one channel), `Bearer` (OAuth2). The prefix is **case-sensitive** — a lowercase one is rejected with `invalid prefix` before the token is looked at, which is why `normalize_token_type` canonicalises everything and falls back to `User`. A User and a Streamer token are both 32-char opaque strings and **cannot be told apart by inspection**, so `resolve_streamer_with_token_type` (settings "Test connection" and the settings *save*, never the runtime tick) retries the other prefixes and reports which worked. 401/403 bodies carry the real reason in `detail`; `_auth_error` maps it (`missing authorization header`, `invalid prefix`, `invalid access token`/`invalid token`, and the 403 `token is not authorized for the requested streamer` → `Forbidden`) instead of answering every failure with `AUTH_MESSAGE` — which used to tell a user who *had* pasted a token to go and add one. Resolve username → streamer id, fetch songs, poll live queue. Treat field *contents* as unverified even when the schema matches the old v1 one: `requests[].name` still exists but comes back `""` for platform requests, with the requester in `requests[].user.username` — `queue_item_view` reads `name` first (manual adds keep free text there) and falls back to the user.
- `sources.py` — artwork search cascade: iTunes (primary) → Last.fm (only if user supplies a key — never hardcode one) → MusicBrainz/Cover Art Archive (release-group level, 1 req/sec, descriptive User-Agent). `rank_candidates` drops artist mismatches (~0.6) and orders the rest: **right song first** (`title_similarity` ≥ 0.8 — nothing checked the title before, so another song by the same artist could win, live on stream too), then not-a-compilation (blocklist terms, or an iTunes `collectionArtistName` that isn't the artist, e.g. "Various Artists"), album over " - Single"/" - EP", exact artist over near miss, **earliest release**. Nothing is rejected outright. iTunes is asked for 10 results at `ITUNES_ART_SIZE` (1000px; it was 600, below the 640px OBS output); `itunes_art_url` rewrites any stored iTunes URL to a size, and `try_download` uses it so old candidate pools fetch at today's size. The ranking was scored against one library's 144 confirmed choices from saved responses (121 vs 107 for the old rule) — rerun that kind of replay before changing it; results drift, so compare variants on the same saved data. Apple often gives a compilation's track the original album's `releaseDate`, so the date alone can't catch every best-of.
- `library.py` — the artwork library: `library/manifest.json` + full-resolution PNGs named `Artist - Title.png`. Statuses: `proposed` / `confirmed` / `unverified` (grabbed live, needs review) / `rejected_all`. The manifest tolerates manually deleted image files (entry reverts to needing art). It does **not** tolerate an unreadable manifest by treating it as empty — that used to happen silently, the next save overwrote the original, and the next sync or live song re-downloaded art over every image on disk, uploads included. Now: saves are atomic and first copy the previous *parseable* version to `manifest.json.bak`; an unreadable or missing manifest is replaced from the `.bak` (unreadable copy kept as `manifest.unreadable-<stamp>.json`); with no usable backup, `Library()` raises `ManifestUnreadable`, so nothing that writes can run. The dashboard answers 503 with the reason, the overlays render with fallback art instead of erroring, the runtime shows the fallback once and retries each tick, and `manifest_problem()` feeds a banner on every page via `/api/runtime/status` (it also keeps each failure to one log line — `Library()` is built per request). `save_image_bytes(entry, data)` never overwrites a confirmed or uploaded image, or a file another entry references; those get `Artist - Title (2).png`. Only the entry's own machine-picked art is replaced in place.
- `artwork.py` — shared artwork logic used by both the runtime service and dashboard request handlers: propose/reject-cycle/upload, plus `resolve_artwork_for_song` (the live lookup order: skip_artists → fallback; library confirmed, else proposed/unverified; live cascade, result saved as `unverified` for post-stream review; fallback + `rejected_all` stub), `apply_fallback`, and `read_song_file`.
- `imaging.py` — resize, reflection effect, and the **atomic PNG save with PermissionError retry** (OBS holds a read handle on the output file — keep this exactly as is). Also the thumbnail cache (`library/thumbs/<content hash>_<size>.webp`, shared by the art wall and the Songs page). `ensure_thumbnail` **renames, never replaces**, into it: the name is the content hash, so an existing file is already the right one, and replacing a file on Windows while another request opens it fails that request with "Permission denied" — a 500 whenever songs sharing a cover were thumbnailed at once. Even a plain rename has a microsecond window where opening the new file fails, so thumbnail responses read it through `fileio.read_bytes` (`dashboard._send_thumbnail`), which retries.
- `runtime.py` — in-process background service (started by the dashboard). One tick polls the queue (feeds the cached queue behind `/overlay/queue.json`) and resolves the current song — queue top, or the song file in `file` mode — to the PNG output via `artwork.resolve_artwork_for_song`. Creates a fresh `Library` per resolve; all manifest I/O is serialised via `library.MANIFEST_LOCK`. Every queue write goes through `_store_queue` — the one place `_empty_since` is maintained, which `empty_for()` exposes to gate the empty-queue promo card. `requests_active()` caches SSL's requests open/closed switch, re-read **only** on ticks that see an empty queue with the promo enabled, so a normal set costs no extra API calls. That state also stops the tick relaxing to `IDLE_INTERVAL` — a closed songlist has to reach the overlay in seconds, and measured on 2026-08-20 the 60s idle tick was exactly what set the lag; a failed check keeps the last answer rather than flipping the card. A rejected credential (401/403) no longer kills the service: `_credential_rejected` parks the streamer id, `_resolve_id` retries at most once per `RESOLVE_RETRY_INTERVAL` (30s) and the tick picks straight back up when the token is fixed — before this the thread returned and stayed dead until a settings save, while every overlay poll fired its own doomed resolve (~4/s, 192 log lines, a 10MB log on 2026-08-31). The same floor is what stops those polls hammering SSL: `get_queue` shares `_resolve_id`, and hands back the last known queue rather than an empty one, so a bad token can never read as "the songlist is empty". Errors carry a kind — `ERROR_AUTH` (the user must act; the dashboard banners it) vs `ERROR_TRANSIENT` (the next poll probably clears it). In `file` mode it runs even without an SSL username (PNG only, empty overlay). The tick waits on a `threading.Event` that `events.EventDoorbell` rings, with `poll_interval` as the timeout — so it is event-driven when the socket is up and timer-driven otherwise.
- `events.py` — subscribes to SSL's Centrifugo realtime events (v2 only) and rings the runtime tick on `queue_*` / `now_playing_*`. It is a **doorbell, not a data feed**: it never parses payloads, because subscriptions carry no state snapshot, `data` is nullable meaning "refetch", and `queue_reorder` is skipped above 1000 entries — REST is the source of truth either way. Anonymous connect (public `streamer:{id}` channels need no token even though every v2 REST read does). asyncio-only SDK, so it owns a private event loop on a daemon thread. **Never load-bearing** — missing dependency, refused connection, or a mid-stream drop all fall back to plain polling.
- `updates.py` — GitHub release check behind the dashboard's update banner. One anonymous `releases/latest` call per launch, on a daemon thread from `run()` — never on a request path, never in the runtime tick. It **never writes `config.json`** (the check timestamp is memory-only) so a background check can't race a settings save; only the user's dismissal writes, from a request thread. Tags are canonicalised to `vX.Y.Z` at store time and compared as int tuples — string comparison puts `1.10.0` below `1.9.0`. Failure is silent everywhere except **Check now**, and a failed re-check keeps the last known release rather than wiping it. It also records the release's `*-Setup-*.exe` asset, which the installed build (`config.FROZEN`) offers as *Download update*; a source run gets only *What's new*.
- `filedialog.py` — the native Browse… dialog, run as a child process by `/api/browse` (tkinter needs its own main thread): `python -m app.filedialog` from source, `<exe> --file-dialog` frozen. It answers through an `--out` file, not stdout, because a windowed build may have no stdout and a pipe decodes with the locale code page.
- `desktop.py` — the tray launcher; what the packaged exe runs (`packaging/entry.py`), and `python -m app.desktop` / `pythonw -m app.desktop` from source. It takes the instance lock, hands a second launch to the running dashboard, calls `dashboard.prepare()`, serves with `make_server` on a thread and runs the pystray icon on the main thread. `--self-check` imports everything a bundle can lose silently (centrifuge, the lazily imported websockets client, tkinter, WebP, certifi, pystray, templates and loaders); `--file-dialog` is how a frozen exe runs `filedialog`. Quitting from the dashboard (`/api/quit`, JSON only, present only when `dashboard.request_quit` is set by the launcher) must also stop the tray loop, or the process outlives its server. The installer uses the same endpoint to close a running copy before upgrading.
- `instance.py` — the single-instance named mutex (`MUTEX_NAME`, shared with the installer's `AppMutex`). `run()` takes it before the port probe, because the probe alone lets two launches a second apart both bind (see the port note below).
- `dashboard.py` — Flask routes; templates in `app/templates/`, CSS in `app/static/`. `/img?key=…` is the full-size library image; with `&s=256` it is a cached WebP thumbnail instead. Anything drawn small must use `entry_view`'s `thumb_url`, not `image_url` — the Songs table used to download every full-size image (222 MB for 186 songs; now ~2.4 MB, lazily). `thumb_url` is versioned by the image file's mtime+size, not `updated_at`, because it is cached `immutable` and a file replaced by hand touches nothing in the manifest. Overlay routes: `/overlay` (settings + OBS URL), `/overlay/queue` (transparent browser-source page; style presets, config-driven with query-param overrides), `/overlay/queue.json` (data; never triggers artwork fetches — library hit or fallback only), `/overlay/current` + `/overlay/current.json` (now-playing card), `/overlay/promo.png` (empty-queue card art: configured image → streamer avatar → fallback).

### Key joints

- `app/__init__.py`'s `__version__` is what the update banner compares against the latest GitHub release tag. If the two drift — tagging `v1.4.0` without bumping it — every user on 1.4.0 is told forever that 1.4.0 is available. `python -m tools.release 1.4.0` bumps, commits and tags in one step so they can't; it refuses on a dirty tree, an existing tag, or a non-increasing version, and does not push.

- The settings API-token field is **never pre-filled** — not with the token, not with a placeholder standing in for it. It used to render a row of `•` and `save_settings` dropped any value starting with one as "that's just the mask", so pasting a new token into the filled box (which appends) silently discarded it and still flashed "Settings saved." An empty box can't be appended to, so blank means keep and anything else is the token. `save_settings` still strips leading bullets, purely so a tab left open on the *old* form can't overwrite a working token with the mask. It also **verifies before reporting success** (`_verify_saved_credential`): the pair is resolved against SSL, a wrong `api_token_type` is corrected in place, and a token SSL *rejects* is discarded in favour of the one already stored — because the field is not pre-filled, anything in that box may have come from a password manager rather than the user, and on 2026-08-31 exactly that replaced a working User token while the page said "Settings saved." and the overlays went dark for five hours. Only a network failure saves unverified, and says so.
- `library.normalize_key(title, artist)` is the shared normalisation (lowercase, strip diacritics/punctuation/`(live)` suffixes) used by **both** dashboard and runtime — it's what makes library lookups hit. Search terms are stripped of suffixes, but library/cache keys use the original title.
- The empty-queue promo card is a **synthetic queue item** built server-side (`_promo_item`) and injected only when an overlay has nothing else to render. Its fixed `id` of `"promo"` is load-bearing: both overlays key their row/card animations on item id, so the constant id keeps it still across polls and makes a real request read as a different item — the swap animates like any other queue change, with no special case in the transition code. Content lives in the shared `promo` config section; each overlay's `show_promo` decides whether it uses it. It has two states, picked from SSL's `requestsActive` switch (`songlist.fetch_requests_active`): the open message, or the `closed_*` one — blank closed text meaning "show nothing while requests are shut". Unknown (no username, every check failed) deliberately reads as **open**; losing the card to a failed API read is worse than showing it a minute late. The two states share the `"promo"` id so open→closed restyles in place instead of animating out and back in.
- Images are stored at source resolution; resize + reflection happen at output time, so config changes never require re-fetching. The art wall's hidden covers (`wall.exclude`) are keyed by each file's **content hash**, so anything that rewrites an image's bytes in place must carry those keys over (as `tools/upgrade_art.py` does) or hidden covers reappear.
- Bulk propose is throttled (~3s/call, iTunes limit ~20/min), runs in a background thread with a polled progress endpoint, and is resumable — never block a request handler on it. A sync starts that same job **scoped to the keys it just added** (`ProposeJob.start(cfg, keys=...)`), because sync creates entries with `status: None` and only the propose flow fills them in — without it a newly added song is invisible to the review queue, which filters on `proposed`/`unverified`. The single-song path `artwork.ensure_proposal` (behind `/api/propose/one`, called by the review card when it lands on an unsearched song) is the one propose that *is* synchronous: it is bounded by one search plus one download, like `/api/more`. It no-ops on any entry that already has a status or an image, so re-opening a card never re-searches and never overwrites a decision.
- Flask binds `127.0.0.1` only. Dashboard port is **5050**, and it is **single-instance**: `run()` connects to the port first and exits rather than starting a second copy. Werkzeug sets `SO_REUSEADDR`, so on Windows a second dashboard binds an already-bound port *successfully* — the two then share it, the older process keeps answering with the code it started with, and both log to the same file, so a restart looks clean while stale code serves the overlays. If an edit doesn't show up over HTTP, check `netstat -ano | findstr :5050` for a second listener before suspecting the code.

## Windows build (`packaging/`)

`powershell -ExecutionPolicy Bypass -File packaginguild.ps1` builds from a clean venv using `requirements-build.txt` (exact pins), then runs PyInstaller on `AlbumArtOverlay.spec` (one-folder, windowed, **no UPX** because it's an antivirus trigger), generates `THIRD-PARTY-NOTICES.txt` from the bundled packages' own licence files (`notices.py`), runs `--self-check` and an HTTP smoke test, builds the per-user Inno Setup installer (`installer.iss`) and writes `SHA256SUMS.txt`, all into `dist/`. The installer's `AppId` GUID must never change. It does not use `AppMutex`: that check runs before anything can close the app, so its `[Code]` asks the running copy to quit via `/api/quit` once the user clicks Install, and only asks the user if that fails. `packaging/icon.ico` is drawn by `make_icon.py` and doubles as the tray icon and `/favicon.ico`.

## Constraints

- Do not commit `config.json`, `library/`, logs, or any API key.
- URL-encode search terms via `requests` params (titles contain `&`, apostrophes); escape quotes in MusicBrainz Lucene queries.
- Filename sanitisation for library PNGs: strip `\/:*?"<>|`, trim trailing dots/spaces, cap length.
- Reject Last.fm's placeholder image (URL containing `2a96cbd8b46e442fc41c2b86b821562f`).
